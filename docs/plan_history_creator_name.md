# 履歴に作成者名を追加する機能 詳細仕様書

## 1. プロジェクト概要

### 1.1 目的
書類生成履歴に、誰が作成したかを示す作成者名を保存・表示し、作成者名でも検索できるようにする。

### 1.2 対象ユーザー
- 株式会社ステップアップの社員（既存の認証済みユーザー）
- 書類生成機能を使用する全ユーザー

### 1.3 機能の位置づけ
- 既存の生成履歴機能の拡張
- 履歴保存・表示・検索機能の一部として実装

## 2. スコープ（やる / やらない）

### 2.1 やること
1. 履歴保存時に作成者名を保存する
2. 履歴一覧画面で作成者名を表示する
3. 最近の履歴画面で作成者名を表示する
4. 履歴検索で作成者名も検索対象に含める
5. 既存の履歴（作成者名がないもの）も正常に表示する（後方互換性）
6. 全履歴を保存できる（localStorageの容量制限内で）

### 2.2 やらないこと
1. 作成者メールアドレスの保存・表示
2. 作成者情報の編集機能
3. 作成者名でのフィルタ機能（検索のみ）
4. 作成者プロフィール画像の保存・表示
5. 履歴の件数上限設定（localStorageの容量制限に依存）
6. 作成者名でのソート機能
7. 作成者名の統計・集計機能
8. 複数ユーザー間での履歴共有機能

## 3. データ定義

### 3.1 HistoryItem型への追加フィールド

| 項目名 | 型 | 必須 | 制約 | 説明 | 取得元 |
|--------|-----|------|------|------|--------|
| createdByName | string | オプション | 最大100文字 | 作成者の名前（表示名） | session.user.name |

### 3.2 データの取得方法
- 作成者名の取得: `session.user.name`（NextAuthのセッションから取得）
- 取得タイミング: 書類生成時（`addHistory`関数を呼び出す際）
- 取得失敗時の処理: 作成者名は保存しない（オプショナルフィールドのため）

### 3.3 データの保存方法
- 保存先: ブラウザのlocalStorage（既存の実装と同じ）
- 保存キー: `stepup_history_${userId}`
- 保存形式: JSON形式の配列

### 3.4 データの制約・バリデーション
- 作成者名の最大文字数: 100文字
- 文字数超過時の処理: 100文字に切り詰める（エラーにしない）
- データ型: string（必須）
- null/undefinedの扱い: オプショナルフィールドのため、存在しない場合は保存しない

### 3.5 既存データとの互換性
- 既存の履歴（作成者名がないもの）: `createdByName`フィールドが存在しない、または`undefined`として扱われる
- 表示時の処理: 作成者名が存在しない場合、「作成者不明」または「-」を表示する
- データマイグレーション: 不要（オプショナルフィールドのため）

### 3.6 全履歴保存について
- 現在の実装: localStorageを使用
- localStorageの容量制限: ブラウザにより異なる（一般的に5-10MB程度）
- 1履歴項目の推定サイズ: 約1-2KB程度（JSON形式、作成者名含む）
- 理論上保存可能な件数: 数千件まで（実用上は十分）
- 容量制限に達した場合: エラーログを出力し、履歴保存を試行する（既存のエラーハンドリングと同じ）
- 容量制限の事前チェック: 実装しない（パフォーマンスのため）

## 6. 例外ケース

### 6.1 作成者名が取得できない場合
- セッションが存在しない場合
  - 処理: 作成者名は保存しない（オプショナルフィールドのため）
  - エラー: 発生しない
- `session.user.name`が存在しない場合
  - 処理: `createdByName`は保存しない
  - エラー: 発生しない
- `session.user.name`が`null`または`undefined`の場合
  - 処理: `createdByName`は保存しない
  - エラー: 発生しない

### 6.2 データの形式が不正な場合
- 作成者名が100文字を超える場合
  - 処理: 100文字に切り詰める（エラーにしない）
  - エラー: 発生しない
- 作成者名が空文字列の場合
  - 処理: 保存しない（オプショナルフィールドのため）
  - エラー: 発生しない
- 作成者名が数値型の場合
  - 処理: 文字列に変換して保存する（型変換）
  - エラー: 発生しない

### 6.3 既存データとの互換性
- 既存の履歴（作成者名がないもの）
  - 処理: `createdByName`が`undefined`または`null`として扱われる
  - 表示: 「作成者不明」または「-」を表示する
  - エラー: 発生しない

### 6.4 権限・セキュリティ
- 認証されていないユーザー
  - 処理: 作成者名は保存しない（セッションが存在しないため）
  - エラー: 発生しない
- 自分の履歴のみ閲覧可能（既存の仕様と同じ）
  - 処理: 他のユーザーの履歴は閲覧できない
  - エラー: 発生しない

### 6.5 localStorageの容量制限
- 容量制限に達した場合
  - 処理: エラーログを出力し、履歴保存を試行する（既存のエラーハンドリングと同じ）
  - エラー: localStorageのQuotaExceededErrorが発生する可能性がある
  - エラーハンドリング: 既存の実装と同じ（エラーログのみ出力）

### 6.6 検索時の例外
- 検索クエリが空の場合
  - 処理: 全履歴を表示する（既存の仕様と同じ）
  - エラー: 発生しない
- 検索クエリに特殊文字が含まれる場合
  - 処理: 部分一致検索として処理する（エスケープ処理は不要）
  - エラー: 発生しない

## 11. データフロー

### 11.1 書類生成時のフロー
1. ユーザーが書類生成ボタンをクリック
2. `/api/generate`エンドポイントにリクエストを送信
3. 書類生成が完了し、PDF・WordファイルのURLが返される
4. クライアント側で`addHistory`関数を呼び出す
5. `session.user.name`から作成者名を取得
6. 作成者名が100文字を超える場合、100文字に切り詰める
7. 履歴項目を作成（作成者名を含む）
8. localStorageに保存

### 11.2 履歴表示時のフロー
1. ユーザーが履歴一覧画面にアクセス
2. `getHistory`関数で履歴を取得
3. 各履歴項目の`createdByName`フィールドを確認
4. `createdByName`が存在する場合、「作成者: [名前]」を表示
5. `createdByName`が存在しない場合、「作成者: -」を表示

### 11.3 履歴検索時のフロー
1. ユーザーが検索クエリを入力
2. `searchHistory`関数を呼び出す
3. 各履歴項目の会社名・代表者名・住所・作成者名を検索
4. 検索クエリに一致する履歴項目を返す
5. 検索結果を表示

## 12. セキュリティ考慮事項

### 12.1 XSS対策
- 作成者名を表示する際、HTMLエスケープを実行する
- Reactのデフォルトのエスケープ機能を利用する（JSXで表示する限り自動的にエスケープされる）

### 12.2 データの整合性
- 作成者名はセッションから取得するため、ユーザーが任意の値を入力できない
- バリデーション処理により、不正なデータが保存されないようにする

### 12.3 プライバシー
- 作成者名は自分の履歴のみ閲覧可能（既存の仕様と同じ）
- 他のユーザーの履歴は閲覧できない
